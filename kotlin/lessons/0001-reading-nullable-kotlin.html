Lesson 1 · 5 minutes

Reading nullable Kotlin.

By the end, you can look at any line that uses ?., ?: or !! in a PR and say exactly what happens when the value is null.

Warm-up: from memory, what does x?.let { f(it) } return when x is null?

null. The ?. stops the chain before let runs, so f is never called. When x isn't null, you get whatever f(x) returns.

You already know three of four.

Kotlin's null operators map almost one to one onto TypeScript.

TypeScriptKotlinWhen the value is null
string | nullString?Only the ? type may hold null (docs)
a?.ba?.bGives null (docs)
a ?? ba ?: bGives b. b is only evaluated when a is null (docs)
a!a!!Throws NullPointerException (docs)
The one that bites TypeScript erases ! at compile time, so it "doesn't change the runtime behavior of your code" (TS handbook). Kotlin's !! is a real check that crashes. Same intent, very different failure.

The Kotlin-only move.

throw and return are expressions, so they can sit after ?:.

private fun titleOf(request: BookRequestDTO): String {
    val title = Titles.normalize(request.title) ?: throw IllegalArgumentException("title must not be blank")
    require(title.length <= MAX_TITLE_LENGTH) { "title must be at most $MAX_TITLE_LENGTH characters" }
    return title
}

normalize returns String?. It gives null when the trimmed title is empty. After the ?: throw, the compiler knows title can't be null, so its type is plain String. In TS you'd write the same thing in two statements: assign, then if (title == null) throw ….

Check yourself.

Answer before you look anything up. Getting it wrong now makes it stick better later.

1 · In titleOf above, request.title is " ". What happens on the val title = … line?

The trimmed title is empty, so normalize returns null. The right side of ?: runs, and that's the throw. Nothing is dereferenced, so there's no NPE.

2 · After that line, what is the type of title?

The only way past the line with a value is the non-null branch, so Kotlin types it String. That's why the next line can call title.length without ?.. (Nothing is the type of the throw itself, which is how this works under the hood.)

3 · Every event class in a shared library has this. What happens if data is null at runtime?

override fun getData(): OrderPlacedEventData {
    return data!!
}
This is the TS-intuition trap. If you read !! like TS's !, you'd expect null to slip through. Kotlin checks it and throws on the spot. Here data is nullable only so the JSON deserialiser can build an empty event; the !! says "by the time anyone calls this, it's set".

4 · findCustomer returns null. What does this line do?

val customer = customerRepository.findCustomer(order.customerId) ?: return null
?: return null is a guard clause. The enclosing function shippingLabelFor exits with null, and on every later line customer is non-null.

Take it to a PR.

Next time you see !! in a diff, ask one question: what guarantees this isn't null? If the answer is "nothing, the helper just returns a nullable", the fix is usually upstream. Here's an example of the pattern:

internal fun storefrontUrlOf(properties: StoreProperties, server: ServerDetails): String =
    properties.publicUrl.orIfBlank("https://${server.host}")!!

private fun String?.orIfBlank(other: String?) = this?.takeIf { it.isNotBlank() } ?: other

The fallback is never null, but orIfBlank is typed to accept a String?, so the result is String? and the caller has to !! it. Typing other as String makes the result String and removes the !!. That's a good, specific review comment.
