Five hops in, one call onward.

A typical setup at a made-up company, Acme: one GKE cluster, namespace default.

  1. Google CloudGKE Ingress → Google HTTPS load balancer web-ingress sends every path (/*) to one Service: edge-nginx. It handles TLS and the public IP, and nothing else.
  2. Service · NodePortedge-nginx Load-balances across the nginx pods.
  3. Pod · nginxnginx, server_name staging.example.com A location /admin { proxy_pass http://$adminapp; } block. This is where path routing happens.
  4. Service · ClusterIPadmin-app Reached by DNS name admin-app.default.svc.cluster.local:80. It forwards to port 8089 on any pod labelled name: admin-app. Internal only.
  5. Pod · distroless Node 24The Next.js app Started and kept alive by a Deployment (replicas: 1). It's only sent traffic once /admin/ping passes readiness.
  6. ClusterIP · never public→ orders-api-internal The app calls an internal API pod-to-pod. No nginx route points at it, so it has no public surface at all.
The surprise Kubernetes has its own Ingress object, so why put nginx behind it? Some teams do this because nginx gives them routing features (rewrites, redirects, per-path headers) that a cloud Ingress lacks, all in one familiar file. The trade-off: GKE Ingress becomes a dumb front door, and one nginx config holds the routing table for every site. A typo there takes them all down.

Why the odd set $var lines.

set $adminapp admin-app.default.svc.cluster.local:80;
…
location /admin {
    proxy_pass http://$adminapp;
}

If proxy_pass names the host directly, nginx looks it up when it boots, and refuses to start if that Service doesn't exist yet (nginx docs: with a variable, the name is resolved at request time). With a variable, the lookup happens per request. So the route can ship before the Service exists. Until the app deploys, that one path returns an error, and every other route keeps working.

So the routing change can go first: it's safe on its own, and the URL works the moment the app's Service appears.

Check yourself.

From memory first. A wrong guess now makes the right answer stick.

1 · Which hop decides that /admin goes to the Next.js app?

GKE Ingress sends /* to nginx and doesn't care about paths. The location block in nginx's config is the real routing table.

2 · The nginx route is deployed, but the app isn't yet. What happens?

The set $var trick moves DNS lookup to request time, so nginx boots fine. Only requests to /admin fail until the Service exists. Without the variable, nginx wouldn't start and every site would be down. That's the danger the trick prevents.

3 · The Next.js pod crashes at 3 am. What restarts it?

The Deployment says one replica should exist. The kubelet restarts a crashed container, and the controller replaces a missing pod. No pm2 is needed. Kubernetes does pm2's job one level up.

4 · Why is the internal API a ClusterIP Service?

ClusterIP is reachable only from inside the cluster. The Next.js app calls it pod-to-pod, and no nginx route points at it, so the internal API has no public surface at all.
