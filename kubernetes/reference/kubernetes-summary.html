Kubernetes for Node developers Overview Summary Lesson 1

Reference

Kubernetes, summarised.

You write down what should be running. Kubernetes keeps making it true, on as many machines as you give it.

The one idea.

Everything else is a consequence of desired state.

You don't tell Kubernetes "start a container". You hand it a YAML file that says "there should be 2 copies of orders-api:gh-812, each with 512 MiB of memory, answering /ping". Controllers then loop forever, comparing what's running against what you asked for and fixing the difference (docs: controllers). A crashed container, a dead machine or a new image tag are all the same event to it: actual state differs from desired, so fix it.

From the Node world pm2 does this for processes on one machine. Kubernetes does it for containers across a cluster of machines. nginx isn't a competitor: it's something you run on Kubernetes to route traffic, which is exactly what Acme does.
You: YAML says "1 × admin-app" → controller compares 0 running → start 1 ↺ forever

The main components.

Two kinds: the machinery (you rarely touch it) and the objects (you write these).

The machinery

A cluster is a control plane plus nodes (docs: components). On GKE, Google runs the control plane for you.

PieceLives onJob
API servercontrol planeThe front door. kubectl, CI and controllers all talk to it.
etcdcontrol planeThe database of desired and actual state.
Schedulercontrol planePicks which node a new pod runs on, based on the CPU/memory it requests.
Controller managercontrol planeThe reconcile loops: "2 replicas wanted, 1 running → start one".
kubeletevery nodeStarts the pod's containers and runs its probes. This is the part doing pm2's job.
kube-proxyevery nodeMakes Service IPs route to the right pods.

The objects you write

ObjectWhat it is
PodOne or more containers that share an IP. The smallest thing Kubernetes runs. Disposable: they die and get replaced, with a new IP.
Deployment"Keep N pods of this image running, and roll out new versions gradually." You almost never create pods directly.
ServiceA stable name and IP that load-balances across pods with matching labels. ClusterIP = internal only; NodePort/LoadBalancer = reachable from outside the cluster.
IngressHTTP routing rules from the outside world ("this host and path → that Service"). On GKE, it becomes a Google load balancer.
ConfigMap / SecretConfig fed into pods as env vars or files, so one image runs in test and prod.
ProbesReadiness: "send me traffic yet?" Liveness: "am I stuck? restart me".
ServiceAccountThe pod's identity. With GKE Workload Identity it maps to a Google service account, so the pod can read a bucket or secret without a key file.
HorizontalPodAutoscalerChanges replicas based on CPU or other metrics. Acme doesn't use one; replica counts are fixed per environment.
NamespaceA folder for objects. Acme puts everything in default and separates test and prod by cluster.

Good at, at a glance.

Reach for it when

  • many services share one platform
  • you need zero-downtime deploys
  • crashes must heal without a human
  • the same image runs in test and prod

Skip it when

  • you have one or two apps
  • it's a database or other heavy state
  • it's local development
  • it's a tiny job or a static site

What it's really good at.

Paraphrasing the official list (overview), ordered by how much Acme leans on it.

Self-healing

Restarts crashed containers, kills ones that fail liveness, and withholds traffic until readiness passes. Nobody gets paged for a single OOM.

Zero-downtime rollouts

New pods start and pass readiness before old ones stop. A bad image never takes all traffic, and rollback is the same mechanism in reverse.

Service discovery

Every Service gets a DNS name. nginx reaches the admin app by name, never by IP, even as pods come and go.

Same image, many environments

Config lives outside the image, so the image tested on staging-gke is the exact one promoted to prod-gke.

Bin packing

Dozens of services share a few machines. The scheduler places pods by their declared CPU and memory requests.

One way to run everything

Java services, Next.js apps and nginx all deploy the same way: an image plus YAML. One platform to learn and monitor, not one per stack.

What it's not good at, and what to use instead.

The docs say it plainly: Kubernetes "is not a traditional, all-inclusive PaaS" (overview).

Weak atWhyUse instead
Small or few servicesA cluster is a lot of moving parts and YAML to keep one or two apps aliveCloud Run (give it an image, it scales to zero), Render/Fly.io, or one VM running docker compose
Databases and other statePods are disposable. Running Postgres well on Kubernetes means owning backups, failover and diskManaged databases. Acme uses Cloud SQL, plus GCS buckets for images, outside the cluster
Building and shipping codeIt "does not deploy source code and does not build your application"CI: GitHub Actions builds the image, Google Cloud Deploy rolls it out
Local developmentA local cluster (minikube, kind) is heavy and slow for a dev loopdocker compose for dependencies (orders-api starts RabbitMQ and a fake GCS this way), app run natively
Tiny event-driven jobsA whole Deployment for a function that runs twice a dayCloud Run jobs + Cloud Scheduler, Cloud Functions, Cloudflare Workers
Static sitesNo server needed at allCDN / object storage (Cloudflare Pages, GCS + CDN)
Running the cluster itselfUpgrades, node pools, networking: a job in itselfA managed control plane (GKE, which Acme uses), or GKE Autopilot, which manages the nodes too
Rule of thumb Kubernetes pays off when you have many services and a team to share the platform. A company with dozens of services usually gets its money back. A side project with one API usually doesn't: Cloud Run gives you most of the benefits with almost no YAML.
